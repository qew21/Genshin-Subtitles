# Activity-log selection is per-cell text plus whole-row copy

Every column of the activity log window renders a read-only, borderless TextBox instead of a TextBlock, so each cell gets native mouse text selection: double-click picks the word bounded by spaces (a contiguous run for CJK — no word segmentation), and drag extends within the cell. A non-empty mouse-made selection is copied to the clipboard the moment the left button is released, silently (copy-on-select); plain clicks, keyboard selections, and row clicks never auto-copy. Ctrl+C and the context menu copy the in-cell text selection when one exists, otherwise the selected rows as headerless TSV (time, region, job, result). Selection never crosses rows or cells — the window stays a virtualized GridView and multi-row copying is whole-row TSV only. A PreviewMouseLeftButtonDown event setter on the row container keeps ListView row selection working, because the TextBox consumes the bubbling click the ListView used to see; in-cell selections of rows scrolled out of the recycling viewport are lost, while the log itself never loses rows.

**Considered Options**: document-style cross-row selection (FlowDocumentScrollViewer or a custom selection layer — a window rewrite that gives up the GridView columns and the existing virtualization for marginal value); row auto-copy on click (every casual row click would clobber the clipboard); a visible copy confirmation (layout and timing logic against the low-cost goal); Chinese word-level double-click segmentation (a tokenizer dependency for a nicety).

**Consequences**: copy-on-select silently overwrites whatever the operator last copied — inherent to the paradigm (PuTTY/X11-style), accepted; the clipboard write retries briefly and fails silently if another process holds the clipboard; follow-tail auto-scroll and log de-noise are untouched, selecting text being a view interaction like any other.
